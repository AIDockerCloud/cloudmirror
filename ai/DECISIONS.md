## DEC-001 — 采纳 PCMP v2.2 作为工程上下文管理协议
日期: 2026-10-24 | 状态: Accepted
- 确认来源: 人类开发者明确指令“参考 AIDockerCloud/PCMP 对本项目做个初始化”
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当协作模式发生根本性改变或 PCMP 推出重大主版本升级时复审
- 背景 (Context): 在长周期与跨会话的 AI 辅助协同开发中，极易发生上下文爆炸、进度失忆、代码与文档不一致等问题，需要规范化的工程状态跟踪体系。
- 决策 (Decision): 采纳 PCMP v2.2 Full 档位规范，在工程中设立 `ai/` 状态真源，引入零外部依赖的 Python 派生索引与合规检查工具 (`scripts/pcmp_index.py`)。
- 理由 (Reason): 纯 Markdown 权威驱动，对 Git 友好，零外部依赖，派生索引可随意删除重建，具备跨模型和跨 IDE 的极致通用性。
- 备选方案 (Alternatives): 依赖单一系统提示词或专有 IDE 插件。放弃理由：缺乏机器级合规自检与长期演进版本跟踪。
- 影响 (Consequences): 团队与智能体遵循统一的接管与收尾协议，每次任务沉淀审计会话并递增 `revision`。

## DEC-002 — 确立“只增不改不删”与双向冲突副本的同步安全策略
日期: 2026-10-24 | 状态: Accepted
- 确认来源: README.md 策略规范与 bw_sync.py 核心设计实现
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当需要支持受控的主动双向覆盖或更精细的字段级三向合并算法时复审
- 背景 (Context): 密码保险库属于个人极高价值安全资产。双向同步过程中若采用基于时钟或先后顺序的自动覆盖机制，极易因网络延迟、时钟偏差或并发修改造成有效密码被覆灭；误删自动传播则可能引发全量清空灾难。
- 决策 (Decision): 系统确立“只增不改不删”核心安全铁律：① 两侧均有时仅对比哈希，相同跳过；② 仅一侧有时在对侧新建；③ 两侧均有但内容不同且发生新变动时，两端均不动原件，各自为对方版本新建一条带有日期标识的“冲突副本”（如 `[冲突副本·YYYY-MM-DD]`），交由人工最终裁决；④ 历史配对条目在单侧消失时，仅记录墓碑并在报告中警示，绝不自动抹除另一侧，亦不复活。
- 理由 (Reason): 将数据破坏与误操作传播风险彻底降至零，宁可保留两份交由人工确认，绝不自动冒进删除或覆盖。
- 备选方案 (Alternatives): 基于 Last-Write-Wins (LWW) 的最后修改时间戳自动覆盖。放弃理由：时间戳不可信且无法表达合并语义，存在严重丢失密码数据的风险。
- 影响 (Consequences): 当发生内容冲突时，需要人类在 Bitwarden 客户端中人工核对并删除多余的冲突副本；系统逻辑高度稳健且具备确定性。

## DEC-003 — 采用官方 Bitwarden CLI 二进制直装与环境变量凭据隔离运行模式
日期: 2026-10-24 | 状态: Accepted
- 确认来源: Dockerfile 与 bw_sync.py 核心运行设计实现
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当 Bitwarden 官方推出专有原生 SDK 或 NodeWarden 协议产生不兼容分歧时复审
- 背景 (Context): 脚本需要通过官方协议与两端自托管服务端通信。若通过 npm 安装 Bitwarden CLI，曾发生过恶意包投毒事件且依赖体积庞大；若两端 CLI 共享默认配置目录，容易产生 session 混淆与登录态冲突；若密码写入配置文件或参数，有泄露风险。
- 决策 (Decision): 容器镜像直接从 GitHub 官方 release 下载固定版本（钉死 2026.10.0）并核对 SHA-256 哈希；脚本通过 `BITWARDENCLI_APPDATA_DIR` 为两端分配独立的配置目录（`bw-node/` 与 `bw-vault/`）；主密码与 API Key 仅经由终端安全输入或环境变量注入，禁止写入配置与持久化文件。
- 理由 (Reason): 保证环境纯净、构建确定可复现并消除 npm 供应链隐患；实现两端登录态与 session 的严格物理隔离；保障凭据生命周期安全。
- 备选方案 (Alternatives): 使用 npm install -g @bitwarden/cli，或在 config.json 中明文配置密码。放弃理由：存在安全漏洞与供应链投毒风险。
- 影响 (Consequences): 容器升级 Bitwarden CLI 时需在 Dockerfile 中显式更新版本号与两端架构哈希；部署需要通过环境变量传递密码。

## DEC-004 — S3 与 Bitwarden 同级归集至统一同步控制台与防重名标签持久化
日期: 2026-10-25 | 状态: Accepted
- 确认来源: 人类开发者明确需求“S3和Bitwarden同级，请将S3的同步也合并到同步控制台里面来操作，按照这个原则来做”
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当需要引入新的跨云对象存储协议（如 WebDAV 或 FTP）或重构多源调度架构时复审
- 背景 (Context): 用户需要管理密码库（Bitwarden）与笔记软件（Obsidian、Joplin、Logseq 等）的多云备份。原架构若将 S3 同步孤立在存储源管理页面，会导致多云操作割裂。需要将 S3 提升至与 Bitwarden 完全同级的核心服务地位，并提供防重名持久化标签、同标签主备桶差异比对、跨云镜像与后台自动定时同步任务。
- 决策 (Decision):
  1. **架构同级 (First-class Peer)**：在【同步执行控制台】设置同级调度选项卡（Bitwarden 保险库同步、S3 笔记同标签主备同步、S3 跨源广播镜像、主备定时同步计划中心），共享统一的可视化差异卡片（相同/新增/冲突/墓碑）与实时终端日志输出窗口；
  2. **防重名与持久化标签**：标签持久化存储于 `data/tags.json`，在创建与修改标签名称时实施大小写不敏感的查重机制，杜绝重名；修改标签名称时自动级联更新所有关联 S3 存储源中的标签配置；
  3. **同标签主备增量同步**：在同一笔记标签下支持选择主桶（Primary）与备桶（Backup），严格按照“只增不改不删”安全策略执行增量比对与写入，备桶独有文件永不抹除；
  4. **原生无依赖轻量调度器**：服务端内置后台定时守护线程，支持每 15 分钟、30 分钟、1 小时至每天等周期的自动增量同步，运行状态与历史流水持久化记录。
- 理由 (Reason): 彻底消除服务层级不对等，保证统一交互体验；纯原生标准库实现，零 pip 依赖，安全可靠。
- 备选方案 (Alternatives): 将 S3 同步保留在 S3 视图，或引入外部 Celery/Redis 进行任务调度。放弃理由：破坏统一控制台体验且违背零外部依赖原则。
- 影响 (Consequences): 前端统一了调度体验，后端维护统一的执行审计流水，所有配置及标签均持久化在 `data/` 目录。

## DEC-005 — 凭据生命周期跟踪与前端防窥探安全展示机制
日期: 2026-10-25 | 状态: Accepted
- 确认来源: 人类开发者明确需求“在录入后开始计算密码的生命周期，界面增加密码使用时长展示，到时间后提示修改密码，界面展示密码提供小眼睛作为开关，关闭则隐藏为*，时长由你判断，从健康-绿色，临期-黄色，到期或过期-红色作为时长字体的颜色”
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当企业合规策略要求自定义密码到期周期（例如 60 天或 180 天）或需要结合系统通知/邮件告警推送时复审
- 背景 (Context): 密码和 S3 访问密钥长时间不轮换存在凭据泄露和持久化利用风险；界面在多人办公或演示环境中若直接暴露明文密码，易造成视觉泄密（shoulder surfing）；用户需要直观了解密码使用时长并在临期与到期时获得明确提示。
- 决策 (Decision):
  1. **生命周期周期基准**：采纳 90 天作为标准凭据安全轮换周期，在凭据录入或修改时自动记录 `password_updated_at`；
  2. **三阶色彩与状态预警**：
     - 健康（< 60 天）：绿色字体（`#10b981`），展示“已使用 X 天 (健康，90天周期)”；
     - 临期（60 ~ 89 天）：黄色字体（`#f59e0b`），展示“已使用 X 天 (临期，剩余 Y 天到期)”；
     - 到期或过期（>= 90 天）：红色字体（`#ef4444`），展示“已使用 X 天 (已过期 Z 天，请尽快修改密码)”，并在卡片弹出过期横幅，提供“立即修改/轮换”快捷操作直接聚焦弹窗输入框；
  3. **小眼睛防窥探开关**：卡片与编辑模态框中的密码/密钥默认隐藏为 `*`（`********`）并显示 `👁️` 按钮；点击后展开真实明文并将图标切换为 `🙈`；再次点击即时恢复星号掩码，兼顾安全性与核验便利性；
  4. **密码变更真实性判定防误判机制**：服务端与前端均实施新旧密码/密钥的严格比对。仅当密码或密钥发生实质性变更时才刷新 `password_updated_at`；若仅修改名称、邮箱、Endpoint、标签等普通配置或直接保存，严格保留原生命周期时间戳，坚决防止误判重置；编辑弹窗中提供实时动态状态徽章，直观提示用户密码是否处于“未修改保留计时”或“已变动重置为0天”。
- 理由 (Reason): 遵循现代安全合规原则，零入侵增强凭据安全感知；纯前端原生计算，结合后端轻量时间戳持久化，不引入额外复杂度。
- 备选方案 (Alternatives): 强制过期锁定或弹窗阻断同步。放弃理由：违背轻量管理原则，可能导致正常同步中断。
- 影响 (Consequences): 数据存储增加 `password_updated_at` 字段；前端源卡片与弹窗具备密码生命周期及小眼睛切换功能。

## DEC-006 — 生产与开发测试配置文件物理隔离与 Profile Switcher 快速切换
日期: 2026-10-25 | 状态: Accepted
- 确认来源: 人类开发者明确需求“我的数据被你覆盖了吗？请新增配置文件可选择，测试开发使用你的测试数据配置文件，当我使用的时候则可以切换到真实配置文件，注意在区分配置文件，不要在开发测试的时候使用真实配置”
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当需要支持多环境（如增加 pre-production 预发环境）或跨设备配置文件云端漫游同步时复审
- 背景 (Context): 密码库同步涉及生产高价值敏感凭据。若开发调试或自动化测试运行时直接读写单一套配置文件（`config.json`），不仅可能误将测试数据覆盖用户真实配置，更可能在演练中误触发向生产保险库写入。必须对真实生产环境与开发测试环境进行物理隔离，提供可视化的快速环境切换与防呆机制，并在自动化测试中杜绝动用真实配置。
- 决策 (Decision):
  1. **双环境配置文件物理隔离**：
     - 生产环境配置（`config.prod.json`）：保留真实生产凭据（NodeWarden Cloudflare 与 Vaultwarden Olares），加入 `.gitignore` 保护不上 Git；
     - 开发测试配置（`config.dev.json`）：包含安全的离线模拟测试节点（`node_dev`, `vault_dev`, `third_dev`），专供功能演练与沙盒调试；
     - 运行态主配置（`config.json`）：激活对应环境时复制生效；
  2. **自动化测试与生产数据 100% 解耦**：测试用例（`tests/test_server.py`）严格仅操作 `config.test.json`，在 `setUpClass` 中快照备份并于 `tearDownClass` 强制二进制还原，严禁自动化测试接触生产配置；
  3. **后端 RESTful Profile 切换机制**：提供 `/api/config/profiles`、`/api/config/switch` 与 `?profile=` 指定环境读写；切换后自动广播更新运行态与数据源；
  4. **前端可视化环境选择器 (Profile Switcher)**：顶部导航增设环境指示胶囊（生产绿色/测试黄色，带脉冲圆点），Tab 7 新增 Profile Switcher 横幅，提供环境选择下拉框与一键激活按钮，并在配置编辑区明确标注目标文件名。
- 理由 (Reason): 物理文件隔离从根本上消除单点配置文件被误写的可能性；测试用例快照自愈确保测试纯净与生产安全；可视化切换赋予用户对环境状态的掌控感。
- 备选方案 (Alternatives): 仅在环境变量中指定环境模式或保持单一配置文件。放弃理由：配置管理不够直观，无法彻底消除本地测试覆写隐患。
- 影响 (Consequences): 项目新增 `config.prod.json` 与 `config.dev.json`；前端顶部与设置区提供环境切换控制；自动化测试获得双重沙箱保护。

## DEC-007 — 域名+账号自然键判定、单端完全重复项安全清理与防重触任务状态机
日期: 2026-10-26 | 状态: Accepted
- 确认来源: 人类开发者明确需求“执行时，日志虽然在打印，但是按钮没有转为执行中或置灰，避免重复点击，容易被认为没有点成功导致点两次，请优化前端任务状态和进度展示，另外比对逻辑是域名加账号，如果都一样才是同一个数据，毕竟一个网站可能注册了不同的账号，另外同一个数据源如果存在重复数据（必须是域名账号密码完全一样），提供重复数据清理”
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当密码条目引入多 URI 跨域绑定、单点登录 (SSO) 凭证关联、或需支持软去重归并历史记录时复审
- 背景 (Context):
  1. 此前同步自然键主要依赖条目名称（name），但同一网站不同账号（如同一域名的个人号与工作号）容易发生混淆或误判冲突；
  2. 真实使用中，同一个数据源因多浏览器导入或重复创建可能沉淀冗余数据，需要精准识别“域名+账号+密码”完全相同的冗余克隆并安全清理；
  3. 前端执行同步/比对时缺少加载状态与防双击锁定，可能导致重复并发提交。
- 决策 (Decision):
  1. **比对逻辑重构为基于域名 (Domain) + 账号 (Username)**：
     - 核心算法重构 `natural_key(norm)`，优先从 URI 提取主机名并归一化（去除 `www.`、小写化、支持 IDN 国际化域名与自定义端口保留），与账号组合为 `(type, domain, username)` 自然键；
     - 允许同一网站注册的不同账号各自独立配对与同步，绝不混淆或冲突；
  2. **单端完全重复数据检测与安全清理 (Strict Deduplication)**：
     - 严格以“域名 + 账号 + 密码”三者完全一致作为重复判定铁律（不满足三者完全相同绝不归类为重复）；
     - 采用“保留原件 + 清理冗余”安全策略：智能甄选收藏状态最高、修改时间最新、字段最全的条目作为唯一永久保留原件（keep item），其余标记为待清理副本（duplicates）；
     - 支持前端交互式扫描、分组预览、密码明文/掩码切换、人工勾选确认后再执行安全清理，严格防止误伤；
  3. **防重触任务状态机与动态进度卡片**：
     - 全局执行锁 `state.isExecuting` 杜绝重复点击与并发冲突；
     - `withTaskExecution` 自动给触发按钮添加禁用状态（disabled）、旋转加载动画（spinner-inline）与动态提示；
     - 控制台终端上方提供实时动态进度条卡片（任务名称、当前步骤描述、耗时秒表与脉冲指示器）。
- 理由 (Reason): 满足多账号同站点的真实使用场景；严苛的重复匹配保证数据零误伤；明确的执行态提升用户交互确定性与系统稳健性。
- 备选方案 (Alternatives): 仅按用户名去重或全字段弱匹配。放弃理由：违背用户“必须是域名账号密码完全一样”的明确要求，容易造成误删。
- 影响 (Consequences): `bw_sync.py` 新增域名提取、自然键重构与 `find_duplicates_in_items`/`clean_duplicates`；`server.py` 新增 `/api/bitwarden/duplicates/scan` 与 `/api/bitwarden/duplicates/clean`；前端新增重复数据检测模态框与任务执行状态管理。

## DEC-008 — 项目名称+账号独立条目判定、自动填充选项规范化、哈希优先配对与回收站联动感知防复活
日期: 2026-10-26 | 状态: Accepted
- 确认来源: 人类开发者明确需求“需要两个数据一致才能算一个独立条目，项目名称，用户名，需要同步的数据是密码和自动填充选项，自动填充选项可能有多个，数据对比是不是包含了回收站的？对比请去掉回收站里面的数据，另外2秒太短了，20s一次吧，同时提供手动刷新”及“请执行”指令
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当 Bitwarden 官方推出新的跨端回收站双向同步 API 或字段级部分同步策略时复审
- 背景 (Context):
  1. 真实运行中出现假重名报警（如 `iforgot.apple.com`、`login.live.com`、`www.qianglie.com` 各有 2 条但密码/填充项两两完全一致，旧算法因多候选直接放弃配对并报歧义；`xn--2os8j.us.ci` 误报）；
  2. 用户指出独立条目以“项目名称 (Name) + 账号 (Username)”为标识，核心同步数据为密码与自动填充选项 (URIs)；
  3. Bitwarden CLI 默认不感知回收站（需 `--trash`），单端放入回收站的条目容易在比对中被误判为未配对而在对端错误复活或引发数量不对等歧义；
  4. 同步任务状态轮询原本 2 秒过频，需放宽至 20 秒并支持随时手动触发。
- 决策 (Decision):
  1. **独立条目判定规则**：自然键以 `(itype, ident, username)` 严格规范化，`ident` 统一去除空格、小写，优先提取域名，无域名时退回规范化项目名称；
  2. **自动填充选项 (URIs) 规范化**：多 URI 排序保证数组顺序无关性，去除空白并保留匹配模式，使得含多项自动填充选项的条目哈希绝对确定且可跨端一致对比；
  3. **精确哈希 1-to-1 优先配对 (Hash-First Matching)**：在同名同账号的多条目场景下，优先匹配内容哈希完全一致的条目，直接 1-to-1 自动配对成功，彻底消解假重名歧义；
  4. **回收站感知联动与防复活墓碑 (Trash-Aware Tombstone)**：引入 `pull_trash()`，若单端条目在对侧回收站中存在相同哈希，精准识别为“在对端已删除”并记入墓碑，绝不误报重名，绝不错误复活；全链路条目统计严格排除回收站条目；
  5. **轮询调优与手动刷新**：前端轮询间隔设为 20 秒倒计时，并提供手动立即刷新按钮。
- 理由 (Reason): 尊重人类真实使用习惯；杜绝假报警与误复活；大幅提升对比算法的智能度与鲁棒性。
- 备选方案 (Alternatives): 保持旧的多对多直接报歧义。放弃理由：产生虚假的人工介入负担，无法解释回收站数据的存在。
- 影响 (Consequences): 4 组重名歧义彻底清零（0 歧义）；回收站删除条目安全沉淀墓碑；前端体验平滑且可随时刷新。

## DEC-009 — S3 模块全链路显式标 DEMO、Bitwarden 同步互斥锁 (409) 与 State 物理隔离

- 确认来源: 人类开发者代码审查指令“请完成P0后提交推送到远程再完成P1推送到远程，再做P2”
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当 P2 阶段完成真实 AWS SigV4 S3 客户端开发，全面移除 DEMO 标签时复审
- 背景 (Context):
  1. 系统在 Bitwarden 线上是具备自测与真实同步能力的原生引擎，而 S3 线上仍处于原型演示阶段（Mock 演算，未接入真实 SigV4 请求）。若界面展示虚假连通与同步状态，易误导用户产生虚假备份安全感；
  2. 后端同步接口缺乏并发互斥锁，快速重触或重复请求可能导致同一配对两实例同时读写引发数据与 state 竞争；
  3. 全局共享单份 `bw-sync-state.json`，在多来源场景下不同配对交替同步会互相覆盖彼此的配对基线与墓碑。
- 决策 (Decision):
  1. **S3 全链路显式标 DEMO**：种子数据全部打上 `[DEMO]` 标识，状态统一置为 `demo`，连通测试与主备同步返回及界面全面注入警示横幅与标记，移除伪造的成功感；
  2. **Bitwarden 同步并发互斥锁**：引入 `ACTIVE_SYNC_PAIRS` 线程锁，若同配对已在后台执行，立即响应 HTTP 409 Conflict 拒绝重复触发；
  3. **State 按 Pair 物理隔离与平滑继承**：引入 `bw-sync-state-{side_a}__{side_b}.json`，首次生成时自动平滑继承原旧基线，`.gitignore` 涵盖所有 pair state 文件。
- 理由 (Reason): 杜绝虚假信心，保障核心同步的并发幂等与多对配对基线物理隔离。
- 备选方案 (Alternatives): 保持全局共享单个 state 文件。放弃理由：多端配对相互污染，不可用。
- 影响 (Consequences): S3 演示边界完全透明化；并发请求得到规范拦截；多配对独立持有各自基线。

## DEC-010 — 冲突副本重试去重、多线程 Web 容器、调度器审计留痕与密码环境变量严格化
日期: 2026-10-26 | 状态: Accepted
- 确认来源: 人类开发者指令“完成P0后提交推送到远程再完成P1推送到远程，再做P2”及“我提交了，请继续”
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当重构同步引擎事务回滚机制或引入三向合并算法时复审
- 背景 (Context):
  1. 同步执行失败未走到 `finalize_state` 时，重新运行会因旧基线再次判定冲突，若目标端已接收部分冲突副本，重试将导致冲突副本指数级增殖；
  2. 原 Web 服务使用单线程 `HTTPServer`，慢速请求易阻塞整个控制台接口；
  3. 后台轻量调度器轮询使用裸 `except: pass` 吞掉异常，缺少失败审计流水，且 `daily_2am` 未准确计算至每日真实凌晨 02:00；
  4. `_password_once` 曾存在回退将配置字段名直接当作明文密码使用的旁路，违反凭据安全铁律。
- 决策 (Decision):
  1. **冲突副本重试去重 (Idempotent Conflict Copies)**：在 `plan_sync` 生成冲突副本决策前，全面检测目标端是否已存在包含相同账号与密码（或笔记内容）的未裁决冲突副本，若已存在同版本副本则跳过创建，即使 state 丢失或重跑多次亦零增殖；
  2. **Web 容器多线程化**：在 `server.py` 中引入 Python 标准库 `ThreadingHTTPServer`，实现多线程并发请求处理；
  3. **后台调度器失败留痕与真实周期**：移除裸 `except: pass`，将调度执行失败及异常统一记入审计任务流水，并引入 `compute_next_run` 准确计算 `daily_2am` 至下一个真实凌晨 02:00；
  4. **彻底移除明文密码回退分支**：在 `_password_once` 中移除将配置字符串当作明文密码使用的后门，强制必须经由指定环境变量或安全终端交互输入注入主密码。
- 理由 (Reason): 实现真正的同步幂等防膨胀，提升服务端并发吞吐量与审计透明度，加固凭据零泄露红线。
- 备选方案 (Alternatives): 依赖全量写入事务回滚。放弃理由：跨第三方 CLI 外部调用难以保证原子事务回滚，目标端去重更为切实可靠。
- 影响 (Consequences): 单元测试扩充至 36 项且全部通过；即使外部网络反复中断，重试亦绝对保证冲突副本不增殖。

## DEC-011 — 原生 AWS SigV4 S3 客户端、思源笔记不可变镜像与环境变量凭据注入
日期: 2026-10-26 | 状态: Accepted
- 确认来源: 人类开发者指令“请完成P0后提交推送到远程再完成P1推送到远程，再做P2”
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当引入其他非 S3 对象存储协议（如 WebDAV）或需要支持多段断点分块并发上传时复审
- 背景 (Context):
  1. 原 S3 模块仅具备前端交互与后台演算 Mock 数据，属于演示壳，未建立真实网络连接与对象比对传输；
  2. 对象存储密钥若直接明文保存在 JSON 配置文件中，存在泄露隐患；
  3. 对于思源笔记（SiYuan）等具备特定块存储特性的知识库，其 `data/` 与 `assets/` 块均以哈希/UUID 命名且具有不可变性，双桶同步需跳过相同大小块以避免重复覆写，且严禁硬删除备桶孤立块。
- 决策 (Decision):
  1. **零 pip 依赖原生 SigV4 S3 客户端 (`RealS3Client`)**：基于 Python 3 原生标准库（`urllib.request`, `hashlib`, `hmac`, `xml.etree.ElementTree`）实现完整 AWS Signature Version 4 签名计算、`ListObjectsV2`（支持 `ContinuationToken` 翻页）、`GetObject`、`PutObject`、`HeadObject` 与 XML 错误解析；
  2. **思源笔记不可变块镜像模式 (`siyuan_block_mirror`)**：检测到“思源笔记”标签时自动启用该策略，相同大小的哈希块直接认定相同并跳过；仅增量写入缺失或变更块；备桶单边孤立块安全保留（零硬删除）；
  3. **环境变量凭据注入安全机制**：S3 存储源配置新增 `access_key_env` 与 `secret_key_env` 支持，运行时优先动态读取宿主环境变量，并在 Web 控制台打上 `[ENV: ...]` 安全标识，避免密钥明文上盘；
  4. **沙箱演示与真实网络平滑共存**：未配置有效密钥或环境变量时继续平滑处于 DEMO 演示保护状态；配置有效真实凭据后即时切换至原生真实 S3 引擎。
- 理由 (Reason): 弥合 S3 演示壳与 Bitwarden 真实引擎的成熟度断层，坚持零 pip 外部依赖约束，落实只增不改不删安全底线与凭据防泄露红线。
- 备选方案 (Alternatives): 引入第三方 boto3 或 minio-py 库。放弃理由：违背本项目全链路 Python 3 原生标准库零 pip 外部依赖核心约束。
- 影响 (Consequences): S3 模块由演示原型蜕变为具备真实跨云同步能力的对象存储备份引擎；单元测试扩充至 43 项且全部通过。

## DEC-012 — Bitwarden 文件夹维度去重与自然键隔离、S3 部分失败真实语义、流式重试与前端 Dry-Run 控制
日期: 2026-10-27 | 状态: Accepted
- 确认来源: 人类开发者明确需求“请优化，另外Bitwarden在对比时加上所属文件夹名称，这样不同文件夹的相同密码就不会报重复了”及交互确认
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当重构文件夹映射层级关系（如嵌套子目录）或引入多段断点分块上传时复审
- 背景 (Context):
  1. 密码保险库中存在跨工作/个人不同文件夹存放同域名且同账号密码的合法需求，原判重键未包含文件夹导致误报重复；
  2. 真实 S3 同步在单个对象异常时仅打印日志但仍返回 `success: True` 且覆盖备桶对象数目，存在“谎报成功”缺陷；
  3. 大对象全包读取存在 OOM 隐患，且网络抖动无退避重试；
  4. 思源笔记指针类对象字典序优先传输易造成备桶快照悬空，非 chunk 路径简单按大小判定容易跳过修改；
  5. 前端 S3 同步按钮硬编码 `apply: true`，缺乏只读预览保护；
  6. 控制台任务历史未展示 `is_real`，难以区分模拟与真实同步。
- 决策 (Decision):
  1. **Bitwarden 文件夹维度去重与自然键隔离**：`find_duplicates_in_items` 判定键扩充为 `(itype, domain, username, password, folder)`，彻底杜绝跨文件夹误报重复；`natural_key` 同步纳入 `folder`；`has_existing_conflict_copy` 修正为全 marker 前缀精确匹配，消除前缀重叠误判；
  2. **S3 部分失败语义与备桶状态保护**：`sync_pair` 引入 `failed_objects` 跟踪，失败数大于 0 时返回 `status: "partial"` 且 `success: False`；备桶 `objects_count` 与 `last_sync` 仅在 100% 成功时更新；
  3. **大对象流式传输与指数退避重试 (`transfer_to`)**：使用 `SpooledTemporaryFile(max_size=8MB)` 进行分块流式直传，大对象自动落盘防 OOM；集成 3 次失败指数退避重试（0.5s, 1s, 2s）；
  4. **思源笔记镜像精细化**：仅 `data/*.sy` 块走纯大小判定，`latest`、`assets/` 附件等一律执行大小 + ETag 复合校验；待传输对象强制先数据块后指针引用；
  5. **前端 Dry-Run 控制与角标闭环**：S3 面板增加只读预览复选框；任务列表与仪表盘显式渲染 `🟢 真实` 与 `🟡 模拟` 角标；
  6. **轻量鉴权与实测耗时**：服务端支持 `CLOUDMIRROR_API_TOKEN` / `--token` 鉴权与指定 host 绑定，记录实测秒级 `duration_s`。
- 理由 (Reason): 满足用户真实的跨目录密码管理习惯，彻底根除“谎报成功”隐患，建立稳定抗网络抖动的大文件传输防线，提升全链路可见度与安全性。
- 备选方案 (Alternatives): 忽略文件夹或强行要求不同密码。放弃理由：违背用户实际生活工作密码隔离管理习惯。
- 影响 (Consequences): 单元测试由 43 项扩充至 51 项且全部通过；自测 12/12 组全部通过；代码与协议规范严格保持一致。
